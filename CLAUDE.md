# Company fork guide

This checkout is the company fork of DefectDojo. The upstream development guide imported above still governs upstream files and upstream contributions; this file adds the fork's own rules. The long-form codebase map lives in the Obsidian vault at `E:\obsisian\hussie\DefectDojo\` (start at `DefectDojo MOC.md`; every subsystem note lists entry points with merge risk).

## Fork facts

- Remotes: `origin` = `Dexter-77Ali/django-DefectDojo` (the fork), `upstream` = `DefectDojo/django-DefectDojo`.
- `master` is a fast-forward-only mirror of `upstream/master`. Never commit on it; the checked-in branch guard blocks edits there.
- `company/main` carries all company work. Topic branches are cut from and merged back into `company/main`. The upstream `dev`/`bugfix` branch check in the imported guide only matters when preparing an upstream contribution.
- Base version 3.4.0 (merged 2026-10-11; the 3.3 weekly patches were merged 2026-09-19, 2026-09-22 and 2026-09-30); current company release `3.3.300-company.1`. Every upstream tag (monthly `x.y.0`, weekly `x.y.N00`) is merged into `company/main` as a real merge commit; see the release-merge checklist in the vault's `Fork Strategy.md`. Since 3.4.0 upstream cuts every release from `dev` (the `bugfix` branch is retired) and merges release PRs without waiting for CI, so the full unit suite after each merge is the company's only gate.
- The company build id is the image tag (`<upstream version>-company.N`, e.g. `3.3.300-company.1`, cut from a CI-green commit after every upstream merge or security fix) plus `DD_FOOTER_VERSION`. The three version files (`dojo/__init__.py`, `components/package.json`, `helm/defectdojo/Chart.yaml`) are never edited.

## Never edit (conflicts on every upstream merge)

`dojo/settings/settings.dist.py`, `dojo/models.py` and every domain `models.py`, `dojo/db_migrations/`, `dojo/templates/base.html`, `dojo/api_v2/*`, `docker-compose.yml` and `docker-compose.override.*.yml`, `Dockerfile.*` (upstream ones; `Dockerfile.company` is company-owned and exempt), `nginx/*.conf`, `helm/defectdojo/*`, the three version files, `AGENTS.md`, `.github/workflows/*` (upstream ones), `LICENSE.md`, `NOTICE`.

If a change truly must land in one of these: smallest possible diff, marked with a `# company:` comment, and try to upstream it first.

## Where company changes go

- **Settings**: `dojo/settings/local_settings.py`, committed (add `!dojo/settings/local_settings.py` to `.gitignore` when the file is created). It runs after `settings.dist.py` in the same namespace via django-split-settings: mutate existing structures (`INSTALLED_APPS += (...)`, `MIDDLEWARE.insert(...)`, `CELERY_BEAT_SCHEDULE[...]`, `_DOJO_TEMPLATE_DIRS.insert(0, ...)`), never re-declare them. The file is exec'd, so use absolute imports. Values travel as `DD_*` environment variables, secrets as `DD_*_FILE`; nothing secret in git.
- **Code**: the company Django app is `dojo/company/` (label `company`, `CompanyConfig` in `dojo/company/apps.py`), chosen 2026-09-19 because it ships through the existing `COPY dojo/` in both images. It has its own migrations (`dojo/company/migrations/`, from `0001_initial`: `RiskAcceptanceRequest`, the only company model; generate new ones with `manage.py makemigrations company` in the uwsgi container, quotes normalised for ruff) and an `AppConfig.ready()` for hook assertions and `signals.connect()`. If an upstream meta-test that scans `dojo/` ever flags it, exempt the package there rather than moving it.
- **URLs**: `ROOT_URLCONF = "dojo.company.urls"` in `local_settings.py`; `dojo/company/urls.py` re-exports `handler400/403/500` from `dojo.urls`, mounts `company_patterns` under `<url_prefix>company/` (URL names start with `company_`) and appends `dojo.urls.urlpatterns`. `PRELOAD_URL_PATTERNS` / `EXTRA_URL_PATTERNS` are for view-free patterns only (importing views there raises `AppRegistryNotReady`).
- **Templates**: company template directory inserted at index 0 of `_DOJO_TEMPLATE_DIRS`; a company `base.html` uses recursive `{% extends "base.html" %}` and overrides only blocks that no upstream leaf template overrides: `header_logo`, `sidebar-items` (company shortcuts from `company/_sidebar.html`, then `{{ block.super }}`), `support-tab`, `dojo_css` (company stylesheet, palette, and for non-staff users the menu declutter in `company/_declutter.html`), `footer`, `tab_bar` (company actions from `company/_quick_actions.html`), `modals` (the findings bulk forms `company.js` moves into the bulk menu), `extra_javascript` (`company.js`) and `settings-dropdown-items` (`{{ block.super }}`, then the EN / Arabic switch). `unittests/company/test_upstream_contract.py` fails when upstream drops one of them. Leaf templates (login, reports, notification `.tpl`) are overridden by mirroring their relative path.
- **Static**: `dojo/static/dojo/company/`, the only location both the dev-mode nginx mount and the nginx image pick up.
- **Data**: `DojoMeta` metadata and tags first; typed columns only as models in the company app with `ForeignKey`/`OneToOneField` to `"dojo.<Model>"`. Never a migration under `dojo/db_migrations`.
- **Hooks that exist for this**: `NOTIFICATION_MANAGER`, `JIRA_CONNECT_METHOD`, `CELERY_TASK_CONTEXT_MANAGERS`, `PARSER_TEST_CLASS_PATH`, the URL hooks above, and the `get_custom_method` registry in `dojo/utils.py:2254` (`FINDING_SLA_PERIOD_METHOD`, `FINDING_SLA_EXPIRATION_CALCULATION_METHOD`, `FINDING_DEDUPE_METHOD`, `FINDING_DEDUPE_BATCH_METHOD`, `FINDING_FALSE_POSITIVE_HISTORY_CANDIDATE_FILTER_METHOD`, `BULK_DELETE_FINDINGS_METHOD`, `FINDING_HASH_METHOD`, `FINDING_COMPUTE_HASH_METHOD`). Dotted paths whose module is missing fail silently: assert every configured hook in `AppConfig.ready()`.
- **Translations**: company strings are translatable (`gettext`, `{% trans %}`); the Arabic catalog is `dojo/company/locale/ar/LC_MESSAGES/django.po`, first in `LOCALE_PATHS` (`local_settings.py`). Only `.po` is committed (upstream ignores `*.mo`); `Dockerfile.company` compiles it with `msgfmt --check`, the dev stack uses a `django.mo` compiled with a throwaway container (commands in `docker/company/README.md`, *Language*). After changing company strings, rerun `makemessages` there and translate the new entries. Notes, risk acceptance names and notification texts are written inside `teams.instance_language()` (the instance `LANGUAGE_CODE`), never in the acting user's UI language. No unit test asserts Arabic text (CI images lack the company msgfmt step). The EN / Arabic switch is `company_set_language` (saves `UserContactInfo.language`, sets the cookie with upstream's `set_language_cookie`).
- **Containers**: `docker-compose.company.yml` layered with explicit `-f` flags (`COMPOSE_FILE` separators differ per OS: `:` on Linux, `;` on Windows). `Dockerfile.company` (company-owned, edit freely) layers `requirements-company.txt` (django-auth-ldap, python-ldap) and the compiled company catalogs on the upstream image: build the upstream image first, then the company layer, both with the same `-f` set minus/plus the company file. Since 3.4.0 `docker-compose.yml` names the upstream images `${DD_IMAGE_REGISTRY:-registry.defectdojo.com}/defectdojo/...` and `docker-compose.company.yml` takes its `BASE_IMAGE` from the same expression, so both builds must see the same `DD_IMAGE_REGISTRY` (leave it unset, or `docker.io` in CI where the loaded images are `defectdojo/...`). Company images are tagged `defectdojo/defectdojo-django:<version>-company`. The `ldap` profile starts a seeded OpenLDAP test directory (`docker/company/ldap/`).
- **Company profiles**: `companies/<name>/<name>.env` (non-secret `DD_COMPANY_*` values, loaded with `docker compose --env-file`) and `companies/<name>/assets/` (artwork). `bash docker/company/apply-profile.sh <name>` copies the artwork into the static tree for a build; never commit profile artwork into `dojo/static`, the tree stays neutral with placeholders. The release workflow takes a `profile` input and suffixes the image tags with it. A variable in a profile reaches the containers only when a compose file references it; `apply-profile.sh` and the `profiles` CI job refuse a profile that sets an unreferenced one. First profile: `zaincash`.
- **LDAP / Active Directory**: `dojo/company/ldap.py` (settings builder, group-to-product-type sync) and `dojo/company/ldap_backend.py` (backend, needs django-auth-ldap). Off unless `DD_COMPANY_LDAP_ENABLED=True`; `DD_COMPANY_LDAP_PROFILE` is `ad` or `openldap`; the admin group grants superuser and staff; groups named `<prefix><product type>` grant that product type, groups named `dojo-team-<team>` (`DD_COMPANY_LDAP_TEAM_GROUP_PREFIX`) put the user in the Django group `team:<team>`, and members of the group DN `DD_COMPANY_LDAP_RISK_APPROVER_GROUP` are put in the Django group `risk-approvers` (never staff), the directory is authoritative for LDAP users on every login (`ldap_backend.sync_directory_access`, shared with `manage.py company_ldap_sync`, which provisions group members before their first login, resyncs directory users outside every group and deactivates those gone from the directory or disabled in AD; directory users carry the Django group `company:directory`). Local `ModelBackend` stays last. LDAPS against an internal CA: the CA PEM goes to `secrets/dd_company_ldap_ca_cert`, read through `DD_COMPANY_LDAP_CA_CERT_PATH` (a path, deliberately not a `_FILE` variable, which `docker/secret-file-loader.sh` would turn into file content). Workstation test: `DD_COMPANY_LDAP_ENABLED=True DD_COMPANY_LDAP_PROFILE=openldap DD_COMPANY_LDAP_BIND_PASSWORD=admin docker compose $F --profile ldap up -d` (seeded users alice/bob/carol/dave/sam; dave is only provisioned by `company_ldap_sync`; alice and sam are in `dojo-security`, add `DD_COMPANY_LDAP_RISK_APPROVER_GROUP=cn=dojo-security,ou=groups,dc=company,dc=test` when the env-file carries a placeholder DN).
- **Teams and assignments**: `dojo/company/teams.py`. Findings carry the tags `team:<team>` and `assignee:<username lower-cased>`; teams are Django groups `team:<team>` (directory groups, or `manage.py company_teams` for local accounts). Findings-list links put several tags in ONE `tags` parameter (`team:a, team:b`, tagulous syntax): repeated `?tags=` keep only the last.
- **Mark fixed**: view `company_mark_fixed` (finding page) / `company_mark_fixed_bulk` (bulk menu), one call of upstream's `finding_helper.close_finding` per finding; upstream's close page when mandatory note types are missing; switch `DD_COMPANY_MARK_FIXED` (default `True`; `False` hides the buttons and refuses the view).
- **Risk acceptance requests**: `dojo/company/risk_requests.py` (request, approve, reject, cancel, extend; approvers hold `company.approve_riskacceptancerequest` through the group `risk-approvers`, `manage.py company_teams --approver <user>`, or superuser; never staff), views `company_risk_request`/`company_risk_inbox`/`company_risk_decide`/`company_risk_expiring` (Expiring tab: Extend for approvers through `ra_helper.reinstate` plus a company note, Let expire through `ra_helper.expire_now` for anyone who may edit the engagement). **Enforcement switch** `DD_COMPANY_RA_APPROVAL_REQUIRED` (off in code, on in `zaincash.env`): `dojo/company/signals.py` refuses non-approvers on every upstream risk acceptance path (pre_save on `Risk_Acceptance` and `Product`, pre_save on `Finding` that saves a newly risk-accepted finding open (imports, copies), `m2m_changed` on `accepted_findings` connected only while the switch is on (a listener costs a query per add), wrappers around `ra_helper.add_findings_to_risk_acceptance`/`simple_risk_accept`/`reinstate`/`expire_now` and `Engagement.copy`, approver check appended to `URL_PERMISSIONS`). Because the dev stack runs with the ZainCash env-file, run upstream unit tests with `docker compose exec -T -e DD_COMPANY_RA_APPROVAL_REQUIRED=False uwsgi ...` (CI runs with the code default, off); company tests pin it with `override_settings`.
- **Modules imported from `local_settings.py`** (like `dojo.company.ldap`) must not import models at module level: settings are still loading and the app registry does not exist yet (`AppRegistryNotReady`). Import models inside functions.
- **Tests and CI**: new files only, `unittests/company/` (with `__init__.py`) and `tests/company_*_test.py`; `.github/workflows/company-ci.yml` that `uses:` upstream's reusable workflows (`ruff.yml`, `build-docker-images-for-testing.yml`, `rest-framework-tests.yml`, `integration-tests.yml`). Upstream's `unit-tests.yml` never triggers for `company/*` branches.
- **Do not revert upstream removals** (SSO moved to Pro in 3.0; Tool Configuration, API pull parsers and dbbackup leave in 3.5). Add replacements as company code.

## Running and testing on this machine

Windows 10, Docker Desktop (WSL 2 backend, disk image on E:), Git Bash, no Python on the host. Docker Desktop does not auto-start.

- The stack runs in dev mode: `docker compose up -d` (UI http://localhost:8080, mailhog http://localhost:8025, Postgres on 5432). `docker-compose.override.yml` is a plain copy of the dev override because Git Bash `ln -s` copies; `docker/setEnv.sh` therefore always reports release mode. Switch modes by passing `-f docker-compose.yml -f docker-compose.override.<mode>.yml` explicitly, or `rm docker-compose.override.yml` to return to release mode.
- Source is bind-mounted at `/app`; uwsgi reloads on `.py` changes, templates re-render per request, static files under `dojo/static/dojo` are served live. Changes to `dojo/settings/local_settings.py` need `docker compose restart uwsgi celeryworker celerybeat nginx` (nginx included: it caches the uwsgi container address and answers 502 otherwise).
- Single test: `bash ./run-unittest.sh -t unittests.company.test_x.TestX -f`, or `docker compose exec -T uwsgi python manage.py test <dotted.path> --keepdb -v2`. CI-equivalent full run uses the `unit_tests_cicd` override (see the Tests and CI note). The shipped skills `defectdojo-dev` (test loop, API token) and `defectdojo-parser` apply.
- `manage.py`, migrations and `scripts/check_migration_leaves.py` run inside the uwsgi container only.
- Lint: `MSYS_NO_PATHCONV=1 docker run --rm -v /e/defectdojo:/app -w /app python:3.14-slim sh -c "pip install -q -r requirements-lint.txt && ruff check --ignore EXE002 ."` (the version CI installs; EXE002 is a false positive on the Windows bind mount)
- Line endings: this clone has `core.autocrlf=false` and `core.eol=lf`; the system gitconfig says `autocrlf=true`, so never re-clone without `--config core.autocrlf=false` or the container entrypoints break.
- Upstream sync:

```bash
git fetch upstream --tags
git checkout master && git merge --ff-only upstream/master && git push origin master
git checkout company/main && git merge <tag>
docker compose build && docker compose up -d
docker compose exec uwsgi python scripts/check_migration_leaves.py
```
